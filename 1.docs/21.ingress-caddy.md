# Caddy with the scafo modules

> `scafo-caddy` is Caddy with two modules: one keeps TLS material in the bucket through the node, the other resolves each request's host from the fleet's routing.

## The two modules

| Module | Caddy module ID | What it does |
|---|---|---|
| TLS storage | `caddy.storage.scafo` | Implements CertMagic's `Storage` and `Locker` by calling the colocated node's `/v1/storage` API. Certificates, private keys, ACME account data and locks live in the bucket; Caddy holds no bucket credential. |
| Dynamic upstreams | `http.reverse_proxy.upstreams.scafo` | Answers `reverse_proxy`'s "where does this request go?" from the routing document the node serves at `/v1/ingress/routes`. No backend address is written in the Caddy configuration. |

Upstream Caddy has neither module, so it cannot route for Scafo at all.

Both modules take the same connection options:

| Option | Meaning |
|---|---|
| `endpoint` | Base URL of the node API, for example `http://127.0.0.1:7400`. A path prefix is preserved. `http` or `https` only. **Required.** |
| `token` | The bearer token, inline. Trimmed. |
| `token_file` | Path to a file holding the token. Read once at startup and trimmed. |

Exactly one of `token` and `token_file`. Setting both, or neither, fails at startup.

::important
`{env.SCAFO_INGRESS_TOKEN}` is resolved during provisioning and never written back: `caddy adapt` and the admin API's `GET /config/` both return the placeholder verbatim. The Caddyfile's other form, `{$SCAFO_INGRESS_TOKEN}`, is substituted before parsing and bakes the secret into the adapted JSON.
::

## Images and flavours

```
ghcr.io/sandros94/scafo-caddy:<version|latest|edge>
ghcr.io/sandros94/scafo-caddy:<version|latest|edge>-dns
```

| Flavour | Contents | Release binaries |
|---|---|---|
| Lean | Caddy plus the two modules | `scafo-caddy-linux-{amd64,arm64}` |
| `-dns` | The same, plus DNS-01 provider plugins for Bunny, Cloudflare, DigitalOcean, Hetzner, OVH and Route 53 | `scafo-caddy-dns-linux-{amd64,arm64}` |

Each binary ships a `.sha256` and is the same binary that is inside the image of its flavour. Every release also carries a `caddy-version` file naming the Caddy both flavours embed.

The lean flavour covers everything but DNS-01: HTTP-01 needs no plugin, and neither does on-demand TLS for customer domains.

Building it yourself:

```sh
xcaddy build --with github.com/sandros94/scafo-ingress
xcaddy build --with github.com/sandros94/scafo-ingress --with github.com/caddy-dns/gandi@v1.0.3
```

## Caddyfile

```caddyfile
{
	email you@example.com

	storage scafo {
		endpoint http://127.0.0.1:7400
		token    {env.SCAFO_INGRESS_TOKEN}
	}

	# Whether a customer domain belongs to this fleet is the node's decision, so
	# this is the one scafo path Caddy calls without a token.
	on_demand_tls {
		ask http://127.0.0.1:7400/v1/ingress/ask
	}
}

(scafo) {
	log {
		output file /var/log/scafo-ingress/access.log
		format json
	}

	reverse_proxy {
		dynamic scafo {
			endpoint http://127.0.0.1:7400
			token    {env.SCAFO_INGRESS_TOKEN}
			prefer   self
		}
		lb_policy     first
		lb_retries    2
		fail_duration 30s
		max_fails     1
	}

	handle_errors {
		@missing vars scafo.route unknown denied
		handle @missing {
			respond "scafo: no deployment answers to {http.vars.scafo.host}" 404
		}
		respond "{err.status_code} {err.status_text}" {err.status_code}
	}
}

# The platform domain and every deployment under it, on one DNS-01 wildcard.
*.apps.example.com, apps.example.com {
	tls {
		dns cloudflare {env.CLOUDFLARE_API_TOKEN}
	}
	import scafo
}

# Customer domains pointed at this fleet.
https:// {
	tls {
		on_demand
	}
	import scafo
}
```

### What each directive does

| Directive | Effect |
|---|---|
| `lb_policy first` | Uses the head of the node's upstream order, which is a priority and never a weighting. |
| `prefer self` | Puts the answering node's own upstreams at the head, so a request stays on the machine it arrived at. |
| `max_fails 1` | **Required with `first`.** `first` picks the first upstream not already marked down, and a dial failure marks one down only after `max_fails` failures — so a higher count sends every retry back to the same dead process and the request fails before the mark is set. |
| `fail_duration 30s` | The window a failed upstream is skipped for; it lets a recovered process back in. |
| `lb_retries 2` | Bounds how long one request keeps trying. An upstream that resolved to nothing resolves to nothing again on the next attempt, so a larger budget only lengthens the wait. |
| `handle_errors` | Turns *no upstream* into a `404` for the cases where the fleet does not serve that host. |

### Request variables

Caddy's answer to *no upstreams* is `503`. The module leaves the status alone and records why in two request variables:

| `scafo.route` | Meaning |
|---|---|
| `ok` | The document named upstreams; a `503` here means they were all unreachable. |
| `unknown` | The fleet does not serve this host. |
| `denied` | A platform API host and a path the ingress must answer itself. |
| `unavailable` | No routing document has arrived yet. A cold start, not a missing deployment. |

`scafo.host` carries the normalized host the lookup was keyed by.

::note
`denied` is answered the same way as `unknown` on purpose: a distinct status would confirm that the path exists. The denial is enforced whatever the error route says.
::

## JSON equivalent

The same configuration as adapted JSON, as in `examples/caddy.json` in the repository. That file also carries a `logging` block defining the `scafo` access logger the `logs` entry below names; it is omitted here:

```json
{
  "storage": {
    "module": "scafo",
    "endpoint": "http://127.0.0.1:7400",
    "token": "{env.SCAFO_INGRESS_TOKEN}"
  },
  "apps": {
    "tls": {
      "automation": {
        "policies": [{ "on_demand": true }],
        "on_demand": {
          "permission": {
            "module": "http",
            "endpoint": "http://127.0.0.1:7400/v1/ingress/ask"
          }
        }
      }
    },
    "http": {
      "servers": {
        "scafo": {
          "listen": [":443"],
          "tls_connection_policies": [{}],
          "routes": [
            {
              "handle": [
                {
                  "handler": "reverse_proxy",
                  "dynamic_upstreams": {
                    "source": "scafo",
                    "endpoint": "http://127.0.0.1:7400",
                    "token": "{env.SCAFO_INGRESS_TOKEN}",
                    "prefer": "self"
                  },
                  "load_balancing": {
                    "selection_policy": { "policy": "first" },
                    "retries": 2,
                    "try_duration": "5s"
                  },
                  "health_checks": {
                    "passive": { "fail_duration": "30s", "max_fails": 1 }
                  }
                }
              ]
            }
          ],
          "errors": {
            "routes": [
              {
                "match": [{ "vars": { "scafo.route": ["unknown", "denied"] } }],
                "handle": [
                  {
                    "handler": "static_response",
                    "status_code": 404,
                    "body": "No deployment answers to this name.\n"
                  }
                ]
              }
            ]
          },
          "logs": { "default_logger_name": "scafo" }
        }
      }
    }
  }
}
```

Operator-authored routes go **ahead** of the dynamic-upstreams catch-all; the first matching route wins, and nothing rewrites the file.

## Certificates: wildcard or per name

| Approach | Needs | Behaviour |
|---|---|---|
| DNS-01 wildcard for the platform domain | The `-dns` flavour and an API token for the zone | One certificate covers every subdomain; a new deployment is reachable over HTTPS the moment the node starts routing it. The bare apex is not covered by the wildcard and mints its own. |
| HTTP-01 per name | Nothing extra; runs on the lean flavour | Correct, but each new subdomain waits for its own issuance the first time it is asked for. |
| On-demand TLS | Nothing extra | For customer domains. Each name is issued once the node's `ask` endpoint agrees to it. |

## `prefer` and `poll_interval`

| Option | Default | Meaning |
|---|---|---|
| `prefer` | `self` | Whose upstreams head every route. `self` is the node answering; any other value is a node id sent through verbatim; `none` asks for nothing and leaves the fleet's own order alone. |
| `poll_interval` | `5s` | How long between fetches of the routing document. It bounds how stale a route may be — how long a deployment that just moved keeps being proxied to where it was. |

## One poller, and reloads

A snippet imported into twenty site blocks is twenty module instances, and they share a single poller and a single cached document. Everything with the same `endpoint`, token, `prefer` and `poll_interval` is one conversation with the node, so the fetch happens once per interval however many blocks ask for it.

A reload does not start over. The incoming configuration's handlers pick up the running poller before the outgoing ones let go, so the document answering requests keeps answering across the swap — including when the node is down at that moment. The poller stops only when the last handler using it goes away.

Requests cost a map lookup, not a round trip: the document is fetched in the background and cached, and the lookup key is the request's host lowercased with any port removed.

## Start order

::warning
Start the node before Caddy and stop it after. A Caddy that starts while the node is down has an empty certificate cache and no routing document: TLS fails and every request is `unavailable` until the node returns.
::

A **running** Caddy is not affected by node downtime — handshakes come from the in-memory certificate cache and routes from the last document that parsed. Only background work fails and is retried: renewals, OCSP staple refreshes, a certificate for a new name, a route that changed since the last successful poll.

| Platform | How |
|---|---|
| Compose | `network_mode: "service:<node>"` plus `depends_on: { <node>: { condition: service_healthy } }`. |
| systemd | Order the Caddy unit `After=` the node unit. The installer's unit takes the token through `LoadCredential=` and retries with `Restart=on-failure`, `StartLimitIntervalSec=0` until the node mints it. |
| Kubernetes | Run the node as a sidecar in the Caddy pod with a startup probe. |

Provisioning is loud about configuration and quiet about the node: a missing, unreadable or empty token aborts startup, while a node that does not answer the first routing fetch is a log warning and nothing more.

::warning
Mount the Caddyfile's **directory**, not the file. An editor replaces the file's inode, and a file bind mount keeps pointing at the old one, so `caddy reload` would reload a stale configuration.
::

## Access log

Point Caddy's JSON access log at the path the node is told to tail, and the node counts requests per environment:

```caddyfile
log {
	output file /var/log/scafo-ingress/access.log
	format json
}
```

```sh
scafo sail --observability --ingress-access-log /var/log/scafo-ingress/access.log
```

Both processes need the path: Caddy writes it, the node reads it. In Compose that is a shared volume mounted into both services. `--ingress-access-log` is rejected with `invalid-input` when observability is off.

## Rotating the ingress token

The ordering rule is **the node first, then Caddy**: a reload refills the certificate cache from storage, so Caddy must find a node that already accepts the token it is about to present. Serving is unaffected throughout — a window where Caddy holds a token the node rejects stalls renewals and route updates, not handshakes and requests.

::steps

### Expand

Set `SCAFO_INGRESS_TOKEN="new,old"` on the node — new one first — and restart it. Both are accepted; the node's token file now holds the new one.

### Migrate

Reload each Caddy with the new token, one at a time, on your own schedule. Reloads are graceful.

### Contract

Set `SCAFO_INGRESS_TOKEN="new"` on the node and restart it. The old token stops working.

::

A single node with a single Caddy can skip the expand step: set the new value on both, restart the node, reload Caddy.
