# Caddy modules

> `scafo-ingress`: the two Caddy modules, their builds, images, options and request variables.

Two modules in one repository and one binary. `caddy.storage.scafo` keeps certificates, private keys and ACME account data in a bucket **without giving Caddy the bucket credentials**, by turning every CertMagic storage operation into an HTTP call to a colocated node daemon. `http.reverse_proxy.upstreams.scafo` answers `reverse_proxy`'s question — where does this request go? — from the fleet routing document that same daemon serves.

| Module | Caddy module ID | Go package |
| --- | --- | --- |
| TLS storage | `caddy.storage.scafo` | `github.com/sandros94/scafo-ingress/storage` |
| Dynamic upstreams | `http.reverse_proxy.upstreams.scafo` | `github.com/sandros94/scafo-ingress/ingress` |

Module path: `github.com/sandros94/scafo-ingress`. License: MIT.

## Building

```sh
xcaddy build --with github.com/sandros94/scafo-ingress          # every module here
xcaddy build --with github.com/sandros94/scafo-ingress/storage  # only the storage one
xcaddy build --with github.com/sandros94/scafo-ingress/ingress  # only the upstreams one
```

The repository root imports every module in it, so naming the root compiles them all in; naming a single module compiles that one and nothing else.

### Dockerfile build arguments

The repository's `Dockerfile` does the same inside the official `caddy:<version>-builder` image and copies the result into the matching runtime image.

| Build argument | Default | Meaning |
| --- | --- | --- |
| `CADDY_VERSION` | `2.11.4` | Selects both the xcaddy builder and the runtime base, so the two never drift apart. It is the canonical Caddy pin for the repository: `go.mod`'s Caddy requirement is kept equal to it |
| `DNS_PROVIDERS` | empty | Whitespace-separated list of pinned Go module paths to compile in as well. Empty is the lean flavour |

```sh
docker build -t my-caddy .
docker build -t my-caddy --build-arg CADDY_VERSION=2.10.0 .
docker build -t my-caddy --build-arg DNS_PROVIDERS=github.com/caddy-dns/gandi@v1.0.3 .
```

One Dockerfile and one xcaddy invocation stand behind both published flavours, so a custom build is the published build with a different argument.

### Images, tags and binaries

Published for `linux/amd64` and `linux/arm64`, in two flavours. **Lean** is Caddy with only the two modules above. **`-dns`** is the same build with a curated set of DNS-01 provider plugins compiled in — a Caddy plugin can only arrive at compile time.

| | Image | Release binaries |
| --- | --- | --- |
| Lean | `ghcr.io/sandros94/scafo-caddy:latest`, `:X.Y.Z`, `:edge` | `scafo-caddy-linux-{amd64,arm64}` |
| With providers | `:latest-dns`, `:X.Y.Z-dns`, `:edge-dns` | `scafo-caddy-dns-linux-{amd64,arm64}` |

Each binary ships a `.sha256` alongside it and is the same binary that is inside the image of its flavour, lifted out of that build's builder stage. Every release also carries one `caddy-version` file naming the Caddy both flavours embed.

::note
The lean flavour covers everything but DNS-01: HTTP-01 needs no plugin, and neither does the on-demand TLS that covers customer domains. The providers are there for the wildcard.
::

### DNS providers in the `-dns` flavour

Exact pins, from `dns-providers.txt`, which is the whole list.

| Provider | Go module | Caddy module |
| --- | --- | --- |
| Bunny | `github.com/caddy-dns/bunny@v1.2.0` | `dns.providers.bunny` |
| Cloudflare | `github.com/caddy-dns/cloudflare@v0.2.4` | `dns.providers.cloudflare` |
| DigitalOcean | `github.com/caddy-dns/digitalocean@v0.0.0-20250606074528-04bde2867106` | `dns.providers.digitalocean` |
| Hetzner | `github.com/caddy-dns/hetzner/v2@v2.0.1` | `dns.providers.hetzner` |
| OVH | `github.com/caddy-dns/ovh@v1.1.0` | `dns.providers.ovh` |
| Route 53 | `github.com/caddy-dns/route53@v1.6.2` | `dns.providers.route53` |

The last path element, minus any `/vN` suffix, is the Caddy module name. The release build asserts that every entry registered under that name, so a provider that breaks the convention fails the build rather than going missing quietly. The DigitalOcean pin is a Go pseudo-version because that repository has never cut a tag.

A provider that is not in the list is added the same way the curated ones arrive — `--with github.com/caddy-dns/gandi@v1.0.3` to xcaddy, or the same string in `DNS_PROVIDERS`.

## Connection options

Both modules take the same three options and mean the same thing by them.

| Option | Type | Required | Description |
| --- | --- | --- | --- |
| `endpoint` | string | **yes** | Base URL of the node daemon's API, for example `http://127.0.0.1:7400`. A path prefix is allowed and is preserved. Must use `http` or `https` and must have a host |
| `token` | string | one of | The bearer token, inline. Trimmed of surrounding whitespace |
| `token_file` | path | one of | Path to a file containing the bearer token. Read once at startup and trimmed, so a trailing newline is fine. An empty file is a startup error |

::warning
**Exactly one of `token` and `token_file`.** Setting both is a configuration error, and so is setting neither; both fail at startup, naming both options. Once provisioned the two are indistinguishable.
::

### Placeholders

Every value accepts Caddy's global placeholders, most usefully `{env.VAR}`. Both modules are provisioned before they serve anything, so request-scoped placeholders are not available — only environment and system values.

| Form | Behaviour |
| --- | --- |
| `{env.SCAFO_INGRESS_TOKEN}` | Resolved during provisioning and never written back into the configuration. `caddy adapt` emits the placeholder verbatim, and the admin API's `GET /config/` returns it verbatim, so only the running process holds the token |
| `{$SCAFO_INGRESS_TOKEN}` | Substituted **before** parsing, so it bakes the secret into the adapted JSON |

The token authorizes these two APIs only, and the endpoint is expected to be loopback or an equally private network path. Do not expose a node daemon's API publicly on the strength of the token alone.

## `caddy.storage.scafo`

`storage` is a global option, so it goes in the leading braces block. It takes the connection options and nothing else.

::code-group
```caddyfile [Caddyfile]
{
	storage scafo {
		endpoint http://127.0.0.1:7400
		token    {env.SCAFO_INGRESS_TOKEN}
	}
}

example.com {
	respond "hello"
}
```

```json [JSON]
{
  "storage": {
    "module": "scafo",
    "endpoint": "http://127.0.0.1:7400",
    "token": "{env.SCAFO_INGRESS_TOKEN}"
  }
}
```
::

With a token file instead, which is the better fit wherever a credential manager hands one over as a path:

```caddyfile
{
	storage scafo {
		endpoint   http://127.0.0.1:7400
		token_file /var/lib/scafo/ingress-token
	}
}
```

The module uses a dedicated HTTP client with a **30-second** per-request timeout. That timeout does not bound `Lock`, which blocks until the lock is acquired or its context is done. It performs no retries other than the one-second lock poll.

::

## `http.reverse_proxy.upstreams.scafo`

It goes inside a `reverse_proxy` block, as `dynamic scafo`. Besides the connection options it takes two of its own.

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `prefer` | string | `self` | Whose upstreams should head every route. `self` means the node answering the request. Any other value is a node id, sent through verbatim, and one that names no node in the fleet simply has no effect. `none` asks for nothing — it is read here and not sent, and the daemon then leaves the fleet's own order alone |
| `poll_interval` | duration | `5s` | How long to wait between fetches of the routing document. Must be positive. It bounds how stale a route may be |

::code-group
```caddyfile [Caddyfile]
reverse_proxy {
	dynamic scafo {
		endpoint      http://127.0.0.1:7400
		token         {env.SCAFO_INGRESS_TOKEN}
		prefer        self
		poll_interval 5s
	}
	lb_policy first
}
```

```json [JSON]
{
  "handler": "reverse_proxy",
  "dynamic_upstreams": {
    "source": "scafo",
    "endpoint": "http://127.0.0.1:7400",
    "token": "{env.SCAFO_INGRESS_TOKEN}",
    "prefer": "self",
    "poll_interval": "5s"
  },
  "load_balancing": { "selection_policy": { "policy": "first" } }
}
```
::

::note
`none` is the module's own word. A literal `none` on the wire would be read as the id of a node called "none" and quietly do nothing, so the module omits the parameter instead — and an absent parameter is the only way to ask for the fleet's own order.
::

### Request variables

The module cannot choose a status code — Caddy's answer to *no upstreams* is `503` — so it records why in two request variables and leaves the answer to a `handle_errors` route.

| Variable | Value |
| --- | --- |
| `scafo.route` | `ok`, `denied`, `unknown` or `unavailable` |
| `scafo.host` | The normalized host the lookup was keyed by: the request host, minus any port, lowercased |

| `scafo.route` | Meaning |
| --- | --- |
| `ok` | The document named upstreams for this request. A `503` with `ok` means they were all unreachable |
| `unknown` | The fleet does not serve this host |
| `denied` | The host is a platform API host and the path is one the ingress must answer itself rather than proxy. Enforced whatever the error route says |
| `unavailable` | No routing document has arrived yet, so nothing is known about this host either way. Deliberately not `unknown`: a cold start is not a missing deployment |

Turning the first two into a `404` takes built-in directives only:

```caddyfile
handle_errors {
	@missing vars scafo.route unknown denied
	handle @missing {
		respond "No deployment answers to {http.vars.scafo.host}." 404
	}
	respond "{err.status_code} {err.status_text}" {err.status_code}
}
```

`denied` is answered the same way as `unknown` on purpose: a distinct status would confirm that the path exists.

### The shared poller

**One poller, not one per site block.** A snippet imported into twenty site blocks is twenty instances of this module, and they share a single poller and a single cached document: everything with the same `endpoint`, token, `prefer` and `poll_interval` is one conversation with the daemon. Only what changes the document, or how often it is asked for, splits them apart.

The routing document is fetched in the background and cached, so a request costs a map lookup and no round trip. A `v` other than `1` is refused whole: the module keeps serving the last document it understood.

| Situation | Behaviour |
| --- | --- |
| First fetch, during provisioning | Attempted, so a healthy pair begins already routing. **Its failure does not fail startup** — it is logged and the poller carries on |
| Later fetch failures | Cost nothing: the last document that parsed keeps answering, and the log says so once per state change rather than once per tick |
| Startup failure of the *configuration* | Fails startup. A missing, unreadable or empty token aborts with an error naming the option |
| Reload | The incoming configuration's handlers pick up the running poller **before** the outgoing ones let go of it, so the document keeps answering across the swap — including when the daemon happens to be down. Polling stops only when the last handler using it goes away |

The poller uses a dedicated HTTP client with a **10-second** per-request timeout and waits the interval *between* attempts rather than on a schedule, so a slow answer delays the next request instead of stacking up behind it.

### Load balancing

The daemon returns each route's upstreams in **priority order, never as a weighting**. `lb_policy first` uses the head of that order.

```caddyfile
reverse_proxy {
	dynamic scafo {
		endpoint http://127.0.0.1:7400
		token    {env.SCAFO_INGRESS_TOKEN}
	}

	lb_policy       first
	lb_retries      2
	lb_try_duration 5s

	fail_duration 30s
	max_fails     1
}
```

| Setting | Value | Effect |
| --- | --- | --- |
| `lb_policy` | `first` | Uses the head of the daemon's order and reaches for the rest only when it fails |
| `max_fails` | `1` | **Must stay at 1.** `first` picks the first upstream not yet marked down, and a failed dial does not mark one down until it has failed `max_fails` times — so with a higher value every retry of the same request goes back to the same dead process |
| `fail_duration` | e.g. `30s` | How long a failed upstream stays skipped, and what lets it back in once it is up |
| `lb_retries`, `lb_try_duration` | e.g. `2` and `5s` | Bound how long one request keeps trying. Caddy stops at whichever it reaches first, waiting `lb_try_interval` (250 ms) between attempts |

::warning
A request to an unknown host takes the same "no upstreams" path as a route whose backends are all down, so it spends the same retry budget — about half a second with the values above — before the 503 can become a 404. A dynamic upstream that resolved to nothing resolves to nothing again on the next attempt, so a larger budget only lengthens that wait.
::

## The complete example Caddyfile

```caddyfile
# A complete scafo ingress, using both modules in this repository.
#
# It expects a scafo node daemon on loopback at 127.0.0.1:7400 and one shared
# environment variable, SCAFO_INGRESS_TOKEN. Replace dev.example with your
# platform domain and the DNS provider with yours; everything else is meant to
# be usable as it stands.
#
# The `dns cloudflare` line needs the -dns flavour -- ghcr.io/sandros94/
# scafo-caddy:latest-dns, or scafo-caddy-dns-linux-<arch>. Everything else here
# runs on either flavour, and dropping the tls block puts the whole file on the
# lean one at the cost of per-name HTTP-01 issuance.
#
# See README.md for what each piece is for, and PROTOCOL.md for the contract
# with the daemon.

{
	# Certificates, keys and ACME account data live in the bucket the node
	# daemon owns. Caddy never sees the bucket credentials.
	storage scafo {
		endpoint http://127.0.0.1:7400
		token    {env.SCAFO_INGRESS_TOKEN}
	}

	# The daemon decides which customer domains it will issue for. This
	# endpoint is public-facing input to a private decision, so it is the one
	# scafo path Caddy calls without a token.
	on_demand_tls {
		ask http://127.0.0.1:7400/v1/ingress/ask
	}
}

# Everything both site blocks share: where a request goes, and what happens
# when it goes nowhere.
(scafo) {
	reverse_proxy {
		# Where this request goes is the daemon's answer, polled in the
		# background and cached, not a backend address written down here.
		dynamic scafo {
			endpoint http://127.0.0.1:7400
			token    {env.SCAFO_INGRESS_TOKEN}

			# Put this node's own upstreams first, so a request that
			# arrives here stays here whenever it can. Name another
			# node's id to prefer that one instead, or `none` to take
			# the fleet's own order.
			prefer        self
			poll_interval 5s
		}

		# The daemon's order is a priority, not a weighting, so take it at
		# its word: first is the head of the list, and the rest are reached
		# for only when the head fails.
		#
		# Caddy stops retrying at whichever of lb_retries and
		# lb_try_duration it reaches first, waiting lb_try_interval
		# (250ms) in between -- so this budget is two attempts and about
		# half a second. A request to a host the fleet does not serve
		# spends the same budget before it can be answered as a 404
		# below, and retrying an empty answer never changes it, so keep
		# the retry count low.
		lb_policy       first
		lb_retries      2
		lb_try_duration 5s

		# Passive health checking: an upstream that fails once is skipped for
		# thirty seconds, which is what makes "the rest" above mean anything.
		# Exactly once, because `first` keeps choosing an upstream until it
		# is marked down, and a higher max_fails would spend every retry of
		# one request on the same dead process.
		fail_duration 30s
		max_fails     1
	}

	handle_errors {
		# The module cannot choose a status code -- returning no upstreams is
		# a 503 in Caddy's vocabulary -- so it records why instead, and this
		# is where that becomes an answer. `unknown` is a host the fleet does
		# not serve; `denied` is a fleet API path that must never be proxied,
		# and is answered the same way so as not to confirm it exists.
		@missing vars scafo.route unknown denied
		handle @missing {
			respond <<HTML
				<!DOCTYPE html>
				<html lang="en">
				<head><meta charset="utf-8"><title>Not found</title></head>
				<body style="font: 16px/1.6 system-ui, sans-serif; max-width: 32rem; margin: 12vh auto; padding: 0 1.5rem">
				<h1 style="font-size: 1.25rem">Nothing is served here</h1>
				<p>No deployment answers to <code>{http.vars.scafo.host}</code>.</p>
				<p style="color: #666">scafo</p>
				</body>
				</html>
				HTML 404
		}

		# Everything else keeps the status it had: `ok` with every upstream
		# down, `unavailable` while the daemon has not answered yet, and any
		# other handler error on the way through.
		respond "{err.status_code} {err.status_text}" {err.status_code}
	}
}

# The platform domain and every deployment under it, on one wildcard
# certificate. DNS-01 is the suggested default: it needs no inbound request per
# name, so a deployment is reachable the moment the daemon routes it.
#
# Without the -dns flavour or without DNS credentials, drop the tls block and
# Caddy issues per name over HTTP-01 instead -- correct, but each new subdomain
# then waits for its own issuance.
*.dev.example, dev.example {
	tls {
		dns cloudflare {env.CLOUDFLARE_API_TOKEN}
		resolvers 1.1.1.1
	}
	import scafo
}

# Customer domains pointed at this fleet. Every other name reaching the HTTPS
# port lands here, and the daemon's ask endpoint decides whether it gets a
# certificate at all.
https:// {
	tls {
		on_demand
	}
	import scafo
}
```

## Operational notes

The daemon must be reachable when Caddy **starts**, but not for Caddy to start. A **running** Caddy is not affected by daemon downtime: TLS handshakes are served from the in-memory certificate cache, requests are routed from the last document that parsed, and only background work fails and is retried later — renewals, OCSP staple refreshes, a certificate for a new name, a route that has changed since the last successful poll.

A Caddy that starts or restarts while the daemon is down has an empty certificate cache and no routing document, so TLS fails and every request is `unavailable` until the daemon returns:

- Start the daemon before Caddy and stop it after, so Caddy never outlives it.
- Compose: share the node's network namespace and `depends_on` it.
- systemd: order the Caddy unit `After=` the daemon's.
- Kubernetes: run the daemon as a sidecar in the Caddy pod with a startup probe.

A **reload** is none of those things: it is graceful, and the routing document survives it along with the certificate cache.

### Rotating the token

The ordering rule: **the daemon first, then Caddy.** A Caddy reload refills the certificate cache from storage, so it must find a daemon that already accepts the token it is about to present. Serving is unaffected throughout — a window where Caddy holds a token the daemon rejects stalls renewals and route updates rather than handshakes and requests.

1. Give the daemon both tokens, new first: `SCAFO_INGRESS_TOKEN="new,old"`, and restart it. Both are accepted; the daemon's token file now holds the new one.
2. Reload each Caddy with the new token, at leisure. Reloads are graceful, not restarts.
3. Contract the daemon to `SCAFO_INGRESS_TOKEN="new"` and restart it. The old token stops working.

A single daemon and a single Caddy can skip the expand step: set the new value on both, restart the daemon, reload Caddy.
